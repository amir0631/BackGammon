## Evidence and method

- **Screenshots:** read 52 of the 106 in `docs/ui/screenshots/wallet/`. This covers every screen ID at 390 × 844 in fa and en, plus the 360 × 800, 768 × 1024, 1024 × 768, 1440 × 900, and 844 × 390 shots that exist.
- **Code read in full:** `features/wallet/*`, `components/wallet/*`, `components/flow/TaskFlow.tsx`, `lib/wallet.tsx`, `ConfirmDialog`, `ActionButton`, `SlowNotice`, and the header of `BottomSheet`.
- **Tests:** `e2e/wallet.spec.ts`.
- **i18n:** every static `t("…")` key in the wallet code exists in both `fa.json` and `en.json` (scripted check, 332 calls).
- **Not run:** the dev stack was not running, so I did not walk the flows live. Findings marked "code reading" are deterministic from the source. Please confirm them on device when fixing.

## What works well

- **Money flows:**
  - The cost blocks are complete: amount, fee shown even at 0, recipient receives or paid-to-bank in toman, balance, and balance after.
  - The primary buttons carry the amount.
  - Nothing is pre-filled, and the "Maximum" chip is inactive by default.
- **Idempotency:**
  - The key is created per (recipient, amount) or per amount and reused on retry. The e2e test checks this.
  - "Check status" re-sends the same key.
  - After a network drop, the step can't be left.
- **Ethics:**
  - "Get coins" has the same weight as Send and Withdraw.
  - No shop link appears in any error or ineligible state.
  - WA-04 is neutral: no packages and no suggested amounts.
  - Withdraw stays enabled for suspended users (§12.1).
- **RTL:**
  - Back arrows and chevrons mirror.
  - Sheba, transaction IDs, and bank references are LTR with Latin digits.
  - Signs use U+2212.
  - Dates are Jalali and times are 24-hour in fa. The `IR` prefix sits at the physical left in fa.
- **Accessibility:**
  - Ledger rows are single buttons with "added/deducted" wording.
  - The masked Sheba has a spoken label.
  - Disabled actions use `aria-disabled` and show a visible reason.
  - Status chips and the timeline use icon plus text.
  - Dialogs put initial focus on the safe option.
- **Server resolved open questions well:**
  - Ledger `tx_id` now matches the receipt.
  - `expected_by` is shown on WD-04 from the server.
  - Withdrawal list pagination exists.
  - `TRANSFER_LINKED` and `WITHDRAW_UNDER_REVIEW` are handled.

## Issues

### Blocking

**W-01 · blocking · TR-03 and WD-04 (review steps) · 360 × 800, 390 × 844 portrait, fa and en**
- **What happens:**
  - The sticky footer holds the password field, its helper, any action error or lock banner, the primary button, and the disabled reason. It is about 210 px tall, and about 325 px with an action error (`tr03-linked--en-390x844`).
  - It covers the end of the content:
    - TR-03 at 390 × 844: "Balance after" is cut, and the irreversibility and safety notes are hidden. At 360 × 800, "Balance after" is fully hidden.
    - WD-04 at 360 × 800 and 390 × 844: the bank card, the rate line ("fixed when you submit"), the expected payout date, the cancel note, the notify line, and the safety note are all hidden.
  - The password field is inside the sticky footer. When it is focused, the keyboard leaves almost none of the cost block visible. A user can type the password and confirm without ever seeing "Balance after" or the payout timing.
- **What should happen:** P§2.1 requires the cost block "always shown in full" before confirming. CLAUDE.md's non-negotiable requires the cost, the balance, and the balance after to be shown before the user confirms. The notes (irreversible, rate fixed, timing) must be seen before the password.
- **Fix:**
  - `components/flow/TaskFlow.tsx`: add an inline footer mode (e.g. `footerMode="inline"`). The footer then renders in document flow at the end of the content, not `position: sticky`. It still uses `margin-block-start: auto`, so on short content it rests at the bottom (thumb zone).
  - `TransferScreen.tsx` (TR-03) and `WithdrawScreen.tsx` (WD-04): use it. The order becomes cost block → Change links → bank card (WD-04) → notes → password → action error / lock / "Still working" → primary button. P§2.6 "password directly above the button" still holds.
  - Keep sticky footers on the other steps, which carry only the button.
  - Add an e2e assertion at 360 × 800 and 390 × 844: no fixed or sticky element intersects the `dl` cost block or the notes.
- **Ref:** CLAUDE.md UX non-negotiable (coin spend shows balance after); P§2.1, P§2.6; wallet.md §3.4 step 3, §3.6 step 4, §4 TR-03 and WD-04 content order; AC 13, AC 26.

**W-02 · blocking · all wallet flows · code structure**
- **What happens:** Non-visual wallet rules are written inside `apps/mobile`:
  - `features/wallet/validation.ts`: `parseAmount`, `amountProblem` (the spec-order limit checks), `feeFor`, `cleanUsername`, `ibanDigits`, `ibanProblem` (the ISO 13616 mod-97 check), `bankCode`, `maskPhone`
  - `features/wallet/shared.ts`: `tehranToday`, `windowTime`, `dayOnly`
  - `maskPhone` is also duplicated in `lib/phone.ts`, with different fallback behavior.
  - None of these have unit tests.
- **What should happen:** CLAUDE.md §2 rule 14: no business logic in `apps/*`. Keep all non-visual logic in `packages/*` so Phase 2 (`apps/desktop`) needs no refactor.
- **Fix:**
  - Move the pure functions to a shared package with unit tests. The main agent picks the package. Suggestion:
    - `packages/api-client/src/wallet/rules.ts` for the amount, fee, username, and IBAN rules
    - `packages/i18n` for `maskPhone`, `windowTime`, `dayOnly`, and `tehranToday`
  - Keep only the React hooks (`useAmountErrorText`, `useWalletFormat`) in the app.
  - Delete the duplicate `maskPhone`.
  - Tests: the three Sheba inputs of AC 18, a bad checksum, an unknown bank code, the fee floor with fractional `fee_pct`, and each `amountProblem` branch in order.
- **Ref:** CLAUDE.md §2 rule 14, §4 (`packages/*`), §16 (lint/tests); spec §3.5 step 2.

**W-03 · blocking · all wallet screens · responsive evidence**
- **What happens:**
  - The committed screenshot set runs without `ALL_VIEWPORTS`:
    - Most screens exist only at 390 fa, 390 en, 360 fa, and 1440 fa.
    - States exist only at 390 fa/en.
    - There is no 430 × 932 shot anywhere.
    - 768 × 1024 and 1024 × 768 exist only for WA-01 and WD-06.
    - en exists only at 390 (plus 1024 for two screens).
    - Landscape exists only for WA-01 and WD-06. The task flows, WD-07, sheets, and dialogs have none.
  - The screenshots are written only when `UPDATE_SCREENSHOTS` is set. Nothing compares them (`toHaveScreenshot` is never called), so they are not visual regression tests.
  - The one wide portrait that exists (768 × 1024) already shows a layout defect (**W-04**), so the missing matrix hides real problems.
- **What should happen:** Every screen at the six §11.7 viewports in fa and en, portrait and landscape where applicable, as visual regression (§16 "Responsive"). States may stay at 390 fa/en.
- **Fix:** `apps/mobile/e2e/wallet.spec.ts`:
  - Run the screen cases (not every state) on `ALL`: WA-01, WA-02, WA-04, TR-00…TR-05, WD-01…WD-11.
  - Add landscape variants 844 × 390 and 932 × 430 for WA-01, TR-01…TR-04, WD-02…WD-05, WD-06/WD-07, and one sheet (WA-02).
  - Assert with `expect(page).toHaveScreenshot()` against the committed baselines.
  - Regenerate and commit.
- **Ref:** CLAUDE.md §11.7 (last rule), §16 Responsive; wallet.md AC 2 ("visual regression"), AC 36.

**W-04 · blocking · WA-04 Get coins · all viewports** (pre-existing string, surfaced here)
- **What happens:**
  - The support channel shown, linked (`mailto:`), and copied is `support@x3d.ir`.
  - It is hardcoded in `support.contact.channel` in both catalogs; it came from the auth step, commit `b2c81c6`.
  - `x3d.ir` is the placeholder domain. While the gateway is off, WA-04 is the only way to get coins, so in production this sends every buyer to a dead address.
- **What should happen:** The domain comes from `BASE_DOMAIN`, and the contact is configurable without a redeploy.
- **Fix:**
  - Main agent: add a registry setting (e.g. `support.contact`, typed string, fa/en description) and expose it in `GET config` (`PublicConfig`).
  - UI: `components/wallet/SupportTopup.tsx` reads it via `usePublicConfig()` and shows the neutral text "Contact support" without a channel until it loads. Remove the literal from `fa.json`/`en.json`, or keep it only as a non-domain fallback label.
- **Ref:** CLAUDE.md §1 (`BASE_DOMAIN` everywhere), §2 rule 7, §14; wallet.md §3.3 step 2.3, AC 8.

### Major

**W-05 · major · WD-06/WD-07 and WA-01 · 768 × 1024 (md portrait), fa and en**
- **What happens:**
  - WA-01 renders as one stretched phone column (`wa01-wallet--fa-768x1024`). The two-column breakpoint is a 40rem container. After the side rail and gutters, 768 leaves about 616 px, so the breakpoint never fires. The three action buttons stretch to about 200 px each.
  - WD-06 is also single column (`wd06-list--fa-768x1024`), because its breakpoint is a 44rem container. WD-07 opens full screen instead of beside the list.
  - The same applies to every md width from 600 to about 800 px.
- **What should happen:** md shows start column (summary, actions, links) | history on WA-01, and list | detail on WD-06/WD-07, with the URL following the selection. Wider screens get more panels, not stretched content.
- **Fix:**
  - `features/wallet/WalletHomeScreen.tsx`: lower `WIDE` so two columns start at a container of about 36rem, with the summary column `minmax(17.5rem, 22.5rem)`.
  - `features/wallet/WithdrawalsScreens.tsx`: lower `WIDE` to about 36rem, with a list column of about 17.5rem. WD-07's `Facts` already stacks under 18rem.
  - Verify at 600 × 960, 768 × 1024, and 1024 × 768, fa and en.
- **Ref:** CLAUDE.md §11.7 (md row and the "not a stretched phone screen" rule); wallet.md §6 md row, §3.7 step 4; AC 37.

**W-06 · major · TR-02 and WD-03 amount steps · all viewports**
- **What happens:**
  - With an amount that fails a rule (e.g. 400 over a 100-coin remaining limit), pressing Enter (the keyboard's "next") or activating Continue shows only the generic "Enter a valid amount." under the button. The specific field error with `next_available_at` never appears (`tr02-amount-limit--en-390x844`).
  - Cause: `ActionButton` blocks the click, and neither screen passes `onBlockedClick`. The field error is revealed only on blur.
  - "Enter a valid amount" is also wrong for a well-formed number that is simply over the limit.
- **What should happen:** The checks run "on blur and on Continue". Each rule shows its own message, including the Jalali time for the limit.
- **Fix:** In `TransferScreen.tsx` (TR-02) and `WithdrawScreen.tsx` (WD-03):
  - Pass `onBlockedClick={() => { setAmountShown(true); focus the amount input }}` to the Continue `ActionButton`.
  - Make the disabled reason the current problem text (`amountText(problem)`) when there is a value, and keep `*.amount.disabled` only for an empty field.
  - Add an e2e test: type 400 with remaining 100, press Enter, and expect `transfer.amount.error.limit` plus `.limitNext`.
- **Ref:** wallet.md §3.4 step 2.3–2.4, §3.6 step 3.4; P§2.2 (disabled state has a visible, true reason); AC 12, AC 25.

**W-07 · major · WD-05 SMS code (and every masked phone in fa) · all viewports, fa**
- **What happens:**
  - «کد ۵ رقمی به ۰۹۱۲•••••۶۷ پیامک شد» renders as «۰۹۱۲۰۰۰۰۰۶۷» (`wd05-code--fa-390x844`). In Vazirmatn, U+2022 BULLET is visually the same as Persian zero U+06F0.
  - The user reads a real-looking but wrong number (09120000067). That undermines trust at the exact moment we ask for an SMS code.
  - This is deviation 8.
- **What should happen:** The masked part is unmistakably a mask in fa and en.
- **Fix:**
  - In the shared `maskPhone` (after **W-02**), use a mask glyph that can't be read as a digit in either script, e.g. `*` (U+002A), or `✱` if the font has it.
  - Separate the masked run from the digits with a thin space: «۰۹۱۲ ***** ۶۷».
  - Update P§18 and wallet.md §3.6 step 5 examples accordingly (UX).
  - Check the same helper on AU-03, AU-08, and ST-01.
  - The Sheba mask can keep `•`, because Sheba uses Latin digits.
- **Ref:** P§18, P§10; wallet.md §3.6 step 5, AC 28; Nielsen 2 (match with the real world).

### Minor

**W-08 · minor · WA-01 · touch, installed PWA** (deviation 5)
- **What happens:** There is no user-invoked refresh. In a standalone Android PWA there is no browser reload. A user whose friend is sending coins, or who is waiting for a support top-up, can refresh only by leaving the screen or switching apps.
- **What should happen:** The user can refresh on demand.
- **Fix:** `WalletHomeScreen.tsx`: either implement pull-to-refresh (touch only, and not while a sheet is open), or add a visible "Refresh" text button next to `wallet.lastUpdated` in the balance card (always visible, 44 px, new key `wallet.refresh` «به‌روزرسانی» / "Refresh"). Either option satisfies the spec.
- **Ref:** wallet.md §3.1 step 2; Nielsen 3 (user control).

**W-09 · minor · WD-09 Cancel withdrawal · sm** (deviation 3)
- **What happens:** WD-09 is a centered dialog at every width. At 390 × 844 its buttons sit at about 55% of the height (`wd09-cancel--fa-390x844`).
- **What should happen:** P§3 specifies a sheet; P§1 reserves centered dialogs for blocking, time-critical decisions.
- **Fix:** `WithdrawalsScreens.tsx`: render WD-09 with `BottomSheet` (`dismissible={!cancelling}`, footer "Cancel withdrawal" / "Keep request", initial focus "Keep request", same "Check status"). `BottomSheet` already becomes a centered dialog at md/lg.
- **Ref:** P§1, P§3; wallet.md §3.7 step 3, §6.

**W-10 · minor · WA-01 history rows and WD-06 rows at md/lg**
- **What happens:** The selected row is shown only by a gold background fill (`wa02-detail--fa-1440x900`, `wd06` at 1440).
- **What should happen:** Selection has a non-color cue.
- **Fix:** `Ledger.tsx` `RowButton` and `WithdrawalsScreens.tsx` `Row`: on `[aria-current]`, add a 3 px start-edge bar (logical `border-inline-start`) and semibold label text.
- **Ref:** P§13; WCAG 2.2 1.4.1.

**W-11 · minor · WD-07 timeline · rejected and cancelled requests**
- **What happens:** "Waiting for payment (expected by …)" shows a green success check (`state: "done"`) even though no payment happened (`wd07-rejected--fa-390x844`).
- **What should happen:** The step reads as "passed", not "succeeded".
- **Fix:** `WithdrawalsScreens.tsx` `steps`: for rejected or cancelled requests, give the waiting step a new neutral "passed" state (outline dot, `textSecondary`) in `WithdrawalStatus.tsx`.
- **Ref:** P§6.2; Nielsen 1.

**W-12 · minor · WD-07 facts · fa**
- **What happens:** "Request ID" is shown in Persian digits («۳۱», via `f.digits`) and can't be copied. The key `withdrawals.detail.reference` is not in the spec.
- **What should happen:** Identifiers users read to support keep Latin digits and can be copied.
- **Fix:** Render `w.id` in Latin digits inside `<bdi dir="ltr">`, with a `CopyButton` (new key `withdrawals.detail.copyId` «کپی شناسه‌ی درخواست» / "Copy request ID"). UX will add the row and keys to the spec.
- **Ref:** P§10 (identifiers in Latin digits), wallet.md §7.

**W-13 · minor · WD-07 after submit**
- **What happens:** The flow lands on `/wallet/withdrawals/{id}?submitted=1`. The query stays in history, so a reload or a later Back/Forward re-shows "Your request was submitted." and moves focus to it again.
- **What should happen:** The banner and focus happen once, right after submitting.
- **Fix:** `WithdrawScreen.tsx` / `WithdrawalDetail`: pass the flag in history state (or sessionStorage, keyed by id). Or, after the first render, `router.replace` to the clean URL while keeping the banner in component state.
- **Ref:** wallet.md §3.6 step 6, §8 WD-07.

**W-14 · minor · Close/Back in TR, WD, WA-01, WD-06/07 · deep links**
- **What happens:** `hadOrigin` / `window.history.length > 1` is used to decide `router.back()`. When the app was opened from an external link in a tab with prior history, × with no input (or the app-bar back) leaves the app for the previous site.
- **What should happen:** Close and Back stay inside the app.
- **Fix:** Track in-app navigation: set a sessionStorage flag in the app shell on the first client-side route change, or compare `document.referrer` with the same origin. Otherwise fall back to `router.replace` to the documented exit: `/wallet`, the profile for `?to=`, or `/me`.
- **Ref:** wallet.md §2 exits; ia.md §3.5.

**W-15 · minor · WD-05 · keyboard and screen-reader users** (code reading)
- **What happens:** `OtpInput` has `autoFocus`, but `TaskFlow`'s `useEffect([stepKey])` runs after it and moves focus to the h1. The code field is not focused.
- **What should happen:** As on AU-03, the code field is focused after the heading is announced.
- **Fix:** Add a `TaskFlow` prop `initialFocus?: RefObject<HTMLElement>`. It focuses that element after the heading is announced (heading gets `aria-live` or is announced through the title), or focuses it instead of the heading on the code step.
- **Ref:** wallet.md §8 WD-05.

**W-16 · minor · TR-02, WD-03 · screen readers**
- **What happens:** The live preview (`role="status"`) re-announces the fee and "receives" on every keystroke.
- **What should happen:** It is announced on blur only.
- **Fix:** Keep the visible preview without `role="status"`. Mirror its text into a visually hidden polite region that updates on blur of the amount field.
- **Ref:** wallet.md §8 (live regions).

**W-17 · minor · TR-00 suspended · all viewports**
- **What happens:** "Details" appears twice: in the suspension banner and again as a link under the body (`tr00-suspended--en-390x844`).
- **What should happen:** One "Details" per screen.
- **Fix:** In `TransferScreen.tsx`, drop the body link when the shell's suspension banner is visible.
- **Ref:** Nielsen 8 (minimalist design).

**W-18 · minor · TR-03 after `TRANSFER_LINKED` or `TRANSFER_RECIPIENT_NOT_FOUND`**
- **What happens:** "Send {amount} coins" stays enabled, although resending the same recipient can only fail again.
- **What should happen:** The only forward path is changing the recipient.
- **Fix:** In `TransferScreen.tsx`, while `actionError.changeRecipient` is set, block the primary button with `blockedBy` pointing at the error banner, so "Change recipient" is the only way forward.
- **Ref:** Nielsen 5 (error prevention).

**W-19 · minor · TR-02, WD-03 amount fields**
- **What happens:** Large amounts are not grouped while typing ("10000").
- **What should happen:** Grouping separators appear as the user types.
- **Fix:** `components/wallet/AmountField.tsx`: display locale grouping (`٬` / `,`) as the user types, keeping the caret after the same count of digits (the approach `IbanField` already uses), and never converting the script of digits the user typed.
- **Ref:** P§10 (amount input), P§12.

**W-20 · minor · WD flow · accounts with an open antifraud flag** (owner: main agent)
- **What happens:** The block is learned only at submit (`WITHDRAW_UNDER_REVIEW`), after bank, amount, and password or code. `GET wallet` has no flag, so WD-01 can't explain it up front.
- **What should happen:** The user learns before starting.
- **Fix:**
  - Main agent: add `withdraw.blocked: boolean` to `WalletSummary`.
  - UI: add a `blocked` branch to `unavailable()` in `WithdrawScreen.tsx`, using the existing `withdraw.unavailable.blockedTitle` / `.blocked` copy.
- **Ref:** CLAUDE.md §7.12; wallet.md §3.6 step 0 and open question 9.

## Heuristics and thumb reach

- **Nielsen:**
  - Strong on 1 (status: pending summary, timeline, and "Last updated"), 5 (error prevention: recipient card, discard dialogs, idempotency), and 9 (errors are specific and neutral, with a next step).
  - Gaps: 3 (W-08, W-14), 1 (W-11), 2 (W-07), and 8 (W-17).
- **Thumb reach (390 × 844 portrait):**
  - The task-flow primary buttons sit in the bottom 12%.
  - WA-01 actions sit at 41–50% of the height (58% at most with the welcome-coin lines collapsed), within the spec's upper 55% band.
  - After W-01 the review buttons move inline. They reach the bottom of the screen after one scroll, which is acceptable because the scroll passes the cost block.
  - Only WD-09 misses the thumb zone (W-09).

## Verdict

**Changes required.** Four blocking issues (W-01 to W-04) and three major issues (W-05 to W-07) must be fixed and re-screenshot at the full §11.7 matrix. The minor issues can follow in the same or a later PR.
